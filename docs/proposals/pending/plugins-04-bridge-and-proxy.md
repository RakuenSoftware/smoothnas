# Proposal: SmoothNAS Plugins — Bridge Network + nginx Proxy

**Status:** Pending
**Part of:** smoothnas-plugins (Step 4 of 9)
**Depends on:** plugins-02-runtime-integration

---

## Problem

Phases 02 and 03 give plugins flat and tier-bound volumes and a
running container, but networking still relies on whatever default
bridge LXC2Docker provides, and the only way to reach a plugin's
HTTP port is to know the bridge IP and curl it from the host.
Operators expect to point a browser at the SmoothNAS UI and click
"Open" on a plugin card; that needs:

- a tierd-managed bridge network with a stable per-container IP,
- nginx routes from `/plugins/<name>/...` to that IP and port, and
- a clear policy for "ports are exposed via nginx, not by binding
  to the host" so two plugins can both run on internal port 8080
  without conflict.

This phase delivers all three. The iframe page that consumes the
nginx route is phase 07; here we just make `/plugins/<name>/`
actually proxy.

---

## Specification

### Bridge network

tierd creates a single managed Docker network at first start:

```http
POST /networks/create
{
  "Name":   "smoothnas-plugins",
  "Driver": "bridge",
  "IPAM": {
    "Driver": "default",
    "Config": [{ "Subnet": "10.66.0.0/16", "Gateway": "10.66.0.1" }]
  },
  "Options": { "io.smoothnas.managed": "true" }
}
```

The subnet (`10.66.0.0/16`) is chosen to:

- not collide with common LAN ranges (192.168.x.x, 10.0.x.x,
  172.16.x.x);
- not collide with Docker's default `172.17.0.0/16`;
- give 65k addresses, comfortably more than any plausible
  plugin count.

Configurable via `tierd_config.plugin_bridge_subnet` for operators
whose LAN happens to use 10.66.x.x. Changing it requires no
running plugins (containers can't be re-IP'd live without
recreate); tierd refuses the change otherwise.

Every plugin container is attached to this network at create time
via `HostConfig.NetworkMode = "smoothnas-plugins"`. tierd does
**not** request a specific IP — IPAM assigns one, tierd reads it
back from `GET /containers/{id}/json` and stores it in
`plugins.bridge_ip`. The IP is stable across restarts as long as
the container is not recreated (LXC2Docker's IPAM honours this).

### Port exposure model

The Docker create payload omits `HostConfig.PortBindings` for
v1 plugins. Containers listen on their declared ports inside the
container; the host never sees those listeners directly.

`plugin_ports.host_expose` is reserved for phase 09 (gh-runner
egress and similar) but defaults to 0 and has no effect in this
phase.

`plugin_ports.expose=1` means "generate an nginx route to this
port over the bridge IP". `expose=0` means "the container is
listening but only sibling plugins on the bridge can reach it"
(useful for sidecars; v1 has none).

### nginx integration

`tierd/internal/plugin/proxy.go` renders, per installed plugin
with at least one `expose=1` port, a file at:

```
/etc/nginx/conf.d/plugins.d/<plugin-name>.conf
```

Template:

```nginx
# Generated by tierd; do not edit. Plugin: <name>, version: <version>
location ^~ /plugins/<name>/ {
    proxy_pass http://<bridge-ip>:<port>/;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-Prefix /plugins/<name>;

    # WebSocket / upgrade support — many plugin UIs need it
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;

    # Streaming-friendly defaults
    proxy_buffering          off;
    proxy_request_buffering  off;
    proxy_read_timeout       1d;
    proxy_send_timeout       1d;

    # Auth header injection (phase 07 fills the bearer):
    # proxy_set_header Authorization "Bearer <token>";
}
```

Multiple `expose=1` ports per plugin: the first port (by
declaration order) gets `/plugins/<name>/`. Additional ports
get `/plugins/<name>/<port-name>/` so a plugin can declare both
a UI and an API.

The parent SmoothNAS nginx config gains one `include` directive:

```nginx
include /etc/nginx/conf.d/plugins.d/*.conf;
```

Added by `iso/hooks/configure.sh` to the existing
`/etc/nginx/conf.d/tierd.conf` `server { ... }` block, inside
the same `server` that already serves `/api/` and the SmoothNAS
UI.

The `$connection_upgrade` map (used for WebSocket support) is
defined once in the parent nginx config (added by
`iso/hooks/configure.sh`):

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

### nginx reload

Whenever tierd writes, updates, or deletes a `plugins.d/*.conf`
file, it calls:

```
nginx -t && systemctl reload nginx
```

`nginx -t` validation failure rolls back the file change and
returns the validation error to the API caller. tierd does **not**
run a live reload after a failed test — the previous valid config
stays active.

### Firewall integration

The existing `internal/firewall` package gates inbound access to
the SmoothNAS UI port (typically 443). Plugin nginx routes ride on
that same port — no new firewall holes are needed for `expose=1`
plugins. The existing UI access policy automatically applies.

For the future `host_expose=1` mode (phase 09): tierd will call
`internal/firewall.Allow(port, protocol)` at install and
`Deny(port, protocol)` at uninstall. v1 stubs these calls but
they are no-ops.

### Bridge IP discovery and stale state

The container's bridge IP is read once after `Start` and cached
in `plugins.bridge_ip`. On `Restart` (without recreate) the IP
is unchanged. On `Recreate` (e.g. tier-volume rename per phase
03) the IP is re-read; stale cache is detected when the cached
IP no longer appears in `GET /containers/{id}/json`'s
`NetworkSettings.Networks["smoothnas-plugins"].IPAddress`.

The startup reconciliation walk (phase 02) re-reads bridge IPs
for all running plugins and rewrites their nginx config files if
the IP changed (e.g. operator manually destroyed a container —
shouldn't happen but doesn't break us).

### Uninstall extension

Phase 02's uninstall flow gains, after container removal but
before flat-volume deletion:

1. `os.Remove("/etc/nginx/conf.d/plugins.d/<name>.conf")` if it
   exists.
2. `nginx -t && systemctl reload nginx`.
3. (Future, phase 09) `internal/firewall.Deny` for any
   `host_expose=1` ports.

The bridge network itself is **not** removed on plugin uninstall
— it persists for other plugins. It is removed only on
appliance teardown (out of scope) or via an explicit
`tierd-cli runtime reset` (also out of scope; mention only).

## Out of scope

- Profile resolution incl. GPU device passthrough (phase 05)
- Plugins UI page (phase 06)
- The iframe page that *consumes* the proxy route (phase 07)
- Bearer auth injection in proxy_set_header (phase 07 fills the
  template's commented line)
- Reference plugins (phases 08, 09)

## Acceptance

- On a fresh install, tierd creates the `smoothnas-plugins`
  network on first start; `docker network inspect smoothnas-plugins`
  (against the runtime socket) shows the configured subnet.
- Installing the llama.cpp test plugin produces
  `/etc/nginx/conf.d/plugins.d/llama-cpp.conf`, `nginx -t`
  passes, and `curl https://<host>/plugins/llama-cpp/` reaches
  the container (`200 OK`).
- WebSocket support: a plugin exposing a websocket endpoint
  (test fixture) can be opened from a browser through the proxy.
- Two plugins both listening on internal port 8080 install and
  run without conflict; both `/plugins/<a>/` and `/plugins/<b>/`
  reach their respective containers.
- Uninstall removes the conf file, `nginx -t` still passes, the
  bridge network stays.
- `nginx -t` failure (simulated by injecting a bad upstream into
  the template) leaves the previous conf file in place and
  returns the validation error to the caller.
