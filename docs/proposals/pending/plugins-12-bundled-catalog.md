# Proposal: SmoothNAS Plugins — Bundled First-Party Catalog

**Status:** Pending
**Part of:** smoothnas-plugins (Step 12)
**Depends on:** plugins-06-ui (catalog install wizard), the catalog GitHub-token fix (#398)

---

## Problem

The "Install plugins" catalog resolves every entry by fetching the plugin
repo's latest GitHub release from `api.github.com` at browse time. The frontend
holds a fixed list of five first-party repos
(`tierd-ui/src/data/pluginCatalog.ts`) and calls
`GET /api/plugins/catalog/latest?repo=<repo>` for each.

That fetch is the single point of failure for installing **SmoothNAS's own
plugins**:

- **Rate limits.** Unauthenticated, GitHub allows 60 requests/hr per IP, shared
  across every catalog repo. One catalog refresh across five repos exhausts it,
  after which every repo returns **403 Forbidden** — the exact failure operators
  hit. #398 added an optional token (60 → 5000/hr), but that makes the token
  *load-bearing for availability* rather than a nicety.
- **Offline / air-gapped appliances.** A box with no outbound GitHub access can
  never browse or install a plugin, even though the manifests are tiny text and
  the plugin images come from a registry the operator can mirror.

Nothing about install itself needs GitHub: `POST /api/plugins/install` takes the
manifest **by value** (`{manifest: <yaml>, tierAssignments, config}`). GitHub is
only in *discovery*. So the fragility is incidental, not fundamental.

The related observation — "plugins are just docker-compose now" (plugins-11) —
is only half true: the catalog artifact is still a `smoothnas.io/v1` manifest,
and a plugin carries appliance-integration metadata (tiered volumes, config/
secrets, host-port guard, nginx routes, UI embed, GPU profiles, lifecycle) that
plain compose can't express. Collapsing plugins into the core would lose the
independent release cadence and the third-party extension point. The targeted
fix is narrower: **bundle the first-party manifests with the appliance and serve
them locally**, keeping the external fetch only for freshness and third parties.

## Specification

### 1. Bundled snapshot (offline floor)

Embed a snapshot of the first-party manifests in tierd:

```
tierd/internal/api/catalogdata/
  index.json                       # [{id, repo, tagName, releaseUrl, manifests[]}]
  aimee/    smoothnas-plugin-aimee-*.yaml
  gh-runner/ smoothnas-plugin.yaml
  llama-cpp/ smoothnas-plugin*.yaml
  vllm/      smoothnas-plugin*.yaml
  wolf/      smoothnas-plugin*.yaml
```

Regenerated by `scripts/sync-plugin-catalog.sh` from each repo's latest release,
filtering to the manifest assets the catalog already ingests
(`smoothnas-plugin.yaml` / `smoothnas-plugin-*.yaml`; not `index.json` or
`*-profile.yaml`). Loaded once at first use, each manifest run through the same
`ParseManifest` + `ValidateManifest` as the live path so a bad snapshot fails
loudly (a test exercises this over the real embedded data).

### 2. Local-first resolver

`catalogLatest` serves the bundled snapshot for a first-party repo
(`source: "builtin"`) with **zero network**; a non-bundled (third-party) repo
falls through to the existing GitHub fetch (`source: "github"`). Because install
takes the manifest by value, nothing downstream changes — the wizard hands the
same YAML to `POST /install`.

### 3. Background freshness (stale-while-revalidate)

The embedded floor is only as new as the last appliance build, so a connected
box keeps first-party plugins current without putting GitHub back in the request
path:

- Cache the last successful live fetch per repo in `plugin_catalog_cache`
  (migration 00024): `repo, tag_name, response(JSON), fetched_at`.
- Serve the **newer of {embedded floor, cache}** by semver (an unparseable tag
  keeps the validated floor).
- On access, trigger a **best-effort background refresh** when the cache is
  missing/stale (6h TTL), with a per-repo in-flight guard. The served response
  never blocks on or fails with the refresh. The refresh uses the authenticated
  token when configured.

### 4. UI signal

The catalog response gains `source`; the install wizard badges first-party cards
**Bundled** (offline-installable). Community entries render unchanged.

### 5. Keeping the floor honest

`scripts/sync-plugin-catalog.sh` regenerates the snapshot; the
`sync-plugin-catalog` workflow runs it weekly (and on demand) and opens a PR when
the upstream releases have advanced, so the offline floor tracks reality at
build time. The repo list is kept in sync with the frontend catalog list.

---

## What this does and does not do

- **Solves:** 403 / rate-limit and fully-offline install for first-party
  plugins; a deterministic, tested-together floor; the token becomes freshness,
  not availability.
- **Unchanged by design:** image pulls still come from GHCR at `materialise`
  (different host/auth — separate concern); third-party plugins still fetch from
  GitHub; the `smoothnas.io/v1` manifest remains the catalog artifact.

---

## Non-goals / future work

- A UI to add arbitrary third-party catalog repos (the list is still fixed in the
  frontend); the resolver already handles non-bundled repos, so this is additive.
- Pinning bundled manifests by digest, or signing the snapshot.
- Mirroring plugin **images** for a truly air-gapped install (registry concern).
