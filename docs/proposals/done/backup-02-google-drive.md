# Proposal: Backups — Google Drive Method

**Status:** Implemented. Automated validation passes; real-account Google Drive validation remains an operator release check.

**Implementation refinements:** Encryption keys and the recovery kit are prepared through `POST /api/backup/google/recovery` before job creation. The acknowledged preparation is consumed on save, expires after 30 minutes, and is never persisted. Saved keys are never re-exported. Encrypted account/folder destinations stay fixed to match the kit. Excludes use `--exclude-from` so patterns cannot become include rules. Full-storage quota errors remain failures.


**Depends on:** backup-01-schedule.

## Problem

SmoothNAS backups can only reach another machine over NFS, SMB or SSH. There
is no offsite target. A Google One / Google AI Pro plan gives operators
terabytes of Drive storage, which makes a good offsite copy of the data that
matters: documents, music, books, and the operator's own backups. Bulk media
can stay local or go elsewhere.

## Decisions (locked)

- **Engine: rclone.** Add a third backup method, `rclone`, with target type
  `gdrive`. Other rclone back ends (B2, S3) can be added later as new target
  types, without a new method.
- **Sign-in happens in the UI, using Google's device flow.** Google rejects
  OAuth redirect URIs that use plain HTTP, a bare IP address, or a domain
  outside the public suffix list. A LAN-only NAS can't receive a normal OAuth
  redirect. The device flow needs no redirect: SmoothNAS shows a code, and the
  operator approves it at google.com/device on any device.
- **Scope: `drive.file`.** The device flow allows only `drive.file` and
  `drive.appdata` for Drive (not full `drive`). With `drive.file`, SmoothNAS can
  only see files it created itself, which is exactly what a backup tool needs.
- **Encryption is a per-job toggle,** using rclone crypt.
- **The operator brings their own OAuth client.** SmoothNAS doesn't ship a
  shared Google client ID. Each operator creates one in their own Google Cloud
  project, so quotas and consent are theirs.

## Specification

### Operator setup (documented in OPERATIONS.md, linked from the UI)

1. In Google Cloud Console, create a project, enable the **Google Drive API**,
   and create an **OAuth client ID** of type **TVs and Limited Input devices**.
2. Set the OAuth consent screen to **External** and then **publish it to
   Production**. A project left in *Testing* status gets refresh tokens that
   expire after 7 days, so backups would silently stop authenticating after a
   week. The app doesn't need Google verification for personal use. The
   operator just clicks through the "unverified app" warning once.
3. In SmoothNAS, go to **Backups → Google accounts → Connect**, paste the
   client ID and secret, then approve the code that's shown.

The UI warns about step 2 in so many words. It is the one setup mistake that
looks fine on day one and breaks a week later.

### Google accounts

Migration `00031_backup_google_accounts.sql`:

```sql
CREATE TABLE backup_google_accounts (
    id             INTEGER PRIMARY KEY,
    label          TEXT NOT NULL UNIQUE,
    email          TEXT NOT NULL DEFAULT '',
    client_id      TEXT NOT NULL,
    client_secret  TEXT NOT NULL,
    refresh_token  TEXT NOT NULL,
    created_at     TEXT NOT NULL
);
```

Several jobs can share one account. Deleting an account that is still in use
by a job is refused (409), and the response lists the jobs using it.

Sign-in endpoints, under `/api/backup/google/`:

| Endpoint | Does |
|---|---|
| `POST device/start` `{label, client_id, client_secret}` | Calls `https://oauth2.googleapis.com/device/code` with scope `openid email https://www.googleapis.com/auth/drive.file`. Returns `{session_id, user_code, verification_url, expires_in}`. |
| `GET device/{session_id}` | Returns `pending`, `connected` (with the account), `denied`, or `expired`. |
| `DELETE device/{session_id}` | Abandons the attempt. |

tierd polls Google's token endpoint itself, at the `interval` Google returns,
and backs off on `slow_down`. The browser only polls tierd. Pending sessions
live in memory and are lost on restart, so the operator just starts again. When
sign-in succeeds, tierd reads the email from the ID token for display, and
stores only the refresh token. Access tokens are never persisted.

Implement this with `golang.org/x/oauth2` (`Config.DeviceAuth` /
`DeviceAccessToken`), which is a new direct dependency.

### Job fields

`backup_configs` gains:

| Column | Meaning |
|---|---|
| `google_account_id` | FK to `backup_google_accounts`; required when `target_type = gdrive` |
| `excludes` | newline-separated rclone filter patterns, e.g. `/video/**` |
| `encrypt` | 0/1. **Fixed after the first run.** Changing it would mix plaintext and ciphertext in one destination. |
| `crypt_password`, `crypt_salt` | generated by tierd when `encrypt = 1`; never returned by the API after creation |

`remote_path` is the folder in Drive (created if missing). `local_path`,
`direction`, `parallelism`, `delete_mode` and the schedule keep their current
meanings.

### Encryption and the recovery kit

When a job is created with encryption on, tierd generates the crypt password
and salt (32 random bytes each, base64). The create response, and only the
create response, includes a **recovery kit**. The UI makes the operator download
it, or confirm they've copied it, before the job can be saved.

The recovery kit is a text file containing:

- a ready-to-use `rclone.conf` snippet (a crypt remote wrapping a `drive` remote,
  with the passwords already obscured in rclone's own format);
- one paragraph explaining how to restore from any machine with rclone.

**If the NAS is lost and nobody kept the recovery kit, the encrypted backup can't
be recovered.** The UI says so next to the toggle. Filename and directory-name
encryption use rclone's `standard` mode.

### Running rclone

Debian packaging: add `rclone` to `Depends` in `tierd/debian/control`. During
implementation, confirm that trixie's packaged rclone supports `scope =
drive.file`, `--drive-stop-on-upload-limit` and `--use-json-log`. If it doesn't,
pin a minimum version.

tierd never writes an rclone config file. Each run gets its remotes through
environment variables only, which only root can read (`/proc/<pid>/environ`):

```
RCLONE_CONFIG_SNDRIVE_TYPE=drive
RCLONE_CONFIG_SNDRIVE_CLIENT_ID=…  RCLONE_CONFIG_SNDRIVE_CLIENT_SECRET=…
RCLONE_CONFIG_SNDRIVE_SCOPE=drive.file
RCLONE_CONFIG_SNDRIVE_TOKEN={"refresh_token":"…","token_type":"Bearer","expiry":"0001-01-01T00:00:00Z"}
# encrypt=1 only:
RCLONE_CONFIG_SNCRYPT_TYPE=crypt
RCLONE_CONFIG_SNCRYPT_REMOTE=sndrive:<remote_path>
RCLONE_CONFIG_SNCRYPT_PASSWORD=<obscured>  RCLONE_CONFIG_SNCRYPT_PASSWORD2=<obscured>
```

rclone refreshes the access token in memory for the run. The refresh token
never changes, so nothing has to be written back.

Commands:

| Direction | delete_mode | Command |
|---|---|---|
| push | off | `rclone copy <local_path> <remote>` |
| push | on | `rclone sync <local_path> <remote>` (the existing `guardDeleteMode` rules apply) |
| pull (restore) | — | `rclone copy <remote> <local_path>`. Pull never deletes. |

Common flags: `--transfers <parallelism> --checkers <2×parallelism>
--fast-list --drive-stop-on-upload-limit --use-json-log --stats 5s
--stats-log-level NOTICE`, plus one `--filter-from` file (0600, deleted when the
run ends) built from `excludes`. The process runs under `ioprioIdleCmd`, like
rsync.

Progress: parse the JSON stats lines (`stats.bytes`, `totalBytes`,
`transfers`, `totalTransfers`, `speed`) into the existing progress callback, so
the run view looks the same as rsync's.

**Daily upload limit.** When `--drive-stop-on-upload-limit` stops the run, it
ends as **completed** with the summary *"Stopped at Google's daily upload limit
— the next scheduled run continues."* Hitting a quota Google applies on purpose
isn't a failure, and reporting it as one would make every day of a first upload
look broken.

**Redaction.** Before rclone's stderr goes into a run's `error` or `summary`, the
client secret, refresh token and crypt passwords are removed from it. This
reuses the approach in `plugin/compose.redactSecrets`.

### Secrets posture

Client secrets, refresh tokens and crypt passwords are stored as plain SQLite
columns, the same way `smb_pass`, `ssh_pass` and plugin secrets are stored
today. They're never serialized to JSON (`json:"-"`). Sealing secrets at rest
is the hardening follow-up that the plugin-secrets migration already mentions,
and it should cover all of these at once.

### UI

- **Backups → Google accounts:** a list with label, email, the number of jobs
  using each account, and Disconnect. **Connect** opens a dialog: label, client
  ID, client secret, the Production warning, then the device code with a link
  to Google's verification URL and a live status.
- **Backup form:** the method picker gains **Google Drive**. Picking it shows:
  account, Drive folder, excludes (a textarea with an example), Encrypt (locked
  after the first run), delete mode, parallelism and the schedule.
- **Recovery kit step** for encrypted jobs, as described above.
- All new strings go through i18n.

### Example: the job that motivated this

| Field | Value |
|---|---|
| local_path | the `storage` share's mount on the reinstalled NAS (path to be set then) |
| remote_path | `smoothnas/storage` |
| excludes | `/video/**`, `/bittorrent/**`, `/proxmoxbackup/**`, `/isos/**`, `/models/**` |
| encrypt | per operator |
| schedule | daily 02:00 |

That's about 2.2 TiB, which takes roughly 3–4 scheduled runs at the daily
upload limit and then only uploads changes.

## Testing

- **Unit:**
  - environment construction, with and without crypt;
  - the argument matrix (direction × delete_mode × excludes);
  - parsing JSON stats into progress;
  - mapping the upload-limit stop to *completed*;
  - redaction, using every secret kind.
- **Device flow:** an `httptest` stand-in for Google's device/code and token
  endpoints covering `authorization_pending`, `slow_down`, `access_denied`,
  `expired_token` and success.
- **rclone integration (CI):** run real rclone against a `local` back end in
  place of `drive`, with and without crypt. Push, then pull to a fresh
  directory, and compare checksums. Push again with nothing changed, and confirm
  nothing transfers.
- **Live validation (manual, before merge):** on a test VM, connect a real
  account, push a small tree with encryption on, restore it on a different
  machine using only the recovery kit and stock rclone, and compare checksums.

## Known limits

- **`drive.file` belongs to the OAuth client's project.** If the operator later
  connects through a client in a *different* Google Cloud project, SmoothNAS
  can't see the files the old client created. They're still in the operator's
  Drive (visible in the web UI), and the recovery kit, plus a client from the
  original project, still restores them. The account dialog says to reuse the
  same client.
- The first upload is limited by Google's ~750 GB/day cap, not by SmoothNAS.

## Out of scope

- Other rclone back ends (B2, S3, Backblaze Personal). `target_type` leaves
  room for them.
- Versioning or retention inside Drive (rclone `--backup-dir`), and bandwidth
  limits. Both are small follow-ups once the method exists.
